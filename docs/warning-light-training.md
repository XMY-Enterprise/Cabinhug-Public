# 指示灯识别训练手册

本文面向车厂的开发人员，回答一件事：**怎么让 Cabinhug 认出你自己品牌车型的指示灯**——用户拍一张中控屏或仪表盘的照片，助手说出哪几盏灯亮了、是什么级别、手册怎么说。

按顺序照做即可，不需要读源码。前提是已按[逐步部署手册](step-by-step.md)把项目跑起来了。

## 两条路：图标目录匹配与专用检测器

系统里有两条完全不同的路，**它们解决的不是同一个问题**。

| | **路 A · 图标目录匹配** | **路 B · 专用小检测器** |
|---|---|---|
| 要不要训练 | **不要** | 要 |
| 状态 | 生产链路今天走的就是这条 | 离线试验，指标还不能当真实召回 |
| 你要准备的 | 手册里的图标图片 + 一张表 | 底图、负样本、合成集、一台带 GPU/MPS 的机器 |
| 大约耗时 | 半天到两天，看图标多少 | 数天，且没有真实照片就没法验收 |
| 产出 | 「这盏灯是 XX，级别 XX，手册说 XX」 | 只是把「框在哪」这一步换成自己的模型 |

**先做路 A。** 做完路 A 系统就已经能认灯了；路 A 的产出（图标图片 + 目录表）同时是路 B 的原料，反过来不成立。路 B 只在你确认通用视觉模型的**定位**不够用时才值得做。

本文第 1 到第 4 步是路 A，第 5 步之后是路 B。

## 步骤总览

| 步骤 | 做什么 | 预计耗时 |
|---|---|---|
| 1 | 从车主手册裁出图标图片 | 2 到 4 小时，27 枚左右 |
| 2 | 写图标目录表 | 2 到 4 小时 |
| 3 | 建图文索引 | 5 分钟 |
| 4 | 验一次：拿真实照片跑匹配 | 30 分钟 |
| — | **路 A 到此结束，系统已经能认灯** | — |
| 5 | 准备真实屏幕底图 | 看素材来源 |
| 6 | 筛负样本 | 半天 |
| 7 | 标定屏幕定位与图标列的几何常数 | 2 小时，必需 |
| 8 | 合成训练集 | 20 分钟 |
| 9 | 在控制台训练 | 30 分钟 / 30 轮 |
| 10 | 测试验证与误报对照 | 1 小时 |
| 11 | 导出 ONNX | 5 分钟 |

# 路 A：图标目录匹配（不需要训练）

## 第 1 步：从车主手册裁出图标图片

系统靠**把用户照片里的图标与手册里的图标并排比一次**来确认，所以手册图标图片是必需品，不是可选项。没有图片时匹配结果只能说「疑似」，说不了「是」。

**从哪里裁**：车主手册 PDF 里「指示灯」那一节的图标表。按 300 dpi 渲染那几页再逐个裁，比从网页截图清楚得多。

**每张图的要求**：

| 项 | 要求 | 为什么 |
|---|---|---|
| 格式 | PNG，RGBA | 需要透明通道 |
| 背景 | 白底转透明 | 合成时要贴到别的底色上 |
| 高度 | 统一 256 像素，宽度按原比例 | 索引与合成都按高度对齐 |
| 文件名 | `<symbol_id>.png`，如 `brake_system_fault.png` | 与目录表的「图片」列一一对应 |
| 内容 | 只有图标本身，不带说明文字与边框 | 边框会被模型当成图标的一部分 |

放在 `data/kb-src/icons/<你的车型目录>/` 下。目录名用英文小写加连字符，例如 `byd-han`、`nio-es6`。

参考现成的一份：`data/kb-src/icons/tesla-model3/`，27 枚。

## 第 2 步：写图标目录表

在 `data/kb-src/icons/` 下建 `<你的车型目录>-indicators.md`。**文件名必须是目录名加 `-indicators.md`**，系统靠这条约定找到图片目录，不靠猜。

文件头必须有一行 `vehicle:`，写车型串。这一行是车型与目录之间唯一的桥：

```markdown
# 比亚迪汉 仪表指示灯目录

vehicle: BYD 汉 EV/DM-i

| symbol_id | 名称 | class | severity | shape | color | elements | text | 手册锚点 | 原文说明 | 描述子来源 | 图片 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| brake_system_fault | 制动系统故障 | fault | stop | circle | red | exclamation, parentheses | BRAKE | 汉 车主手册 › 指示灯 › 制动系统 | 该红色指示灯亮起说明检测到制动系统故障或制动液液位低，请立即联系服务中心 | manual-image | brake_system_fault.png |
```

**十二列的顺序是固定的**，多一列少一列都解析不出来。逐列说明：

| 列 | 填什么 | 取值 |
|---|---|---|
| `symbol_id` | 英文标识，全仓唯一 | 只能是小写字母、数字、下划线 |
| 名称 | 中文名，**用户看到的就是这个** | 照手册原文 |
| `class` | 类别 | `fault` / `reminder` / `status` |
| `severity` | 级别 | `stop` / `check_soon` / `info`，**不能随便填**，见下 |
| `shape` | 整体形状 | 见下方词表 |
| `color` | 颜色 | 见下方词表 |
| `elements` | 图形元素，逗号分隔 | 见下方词表；没有填 `-` |
| `text` | 图标里的字母或数字 | 如 `BRAKE`、`ABS`；没有填 `-` |
| 手册锚点 | 这条出自手册哪一节 | 形如 `手册 › 章 › 节` |
| 原文说明 | **照抄手册**，不要自己写 | 助手回答时会引用它 |
| 描述子来源 | 这一行的可信度 | `manual-image` / `standard-symbol` / `deprecated` |
| 图片 | 图片文件名 | 如 `abs_fault.png`；没有填 `-` |

### severity 不是自己定的，是算出来的

级别由**类别 × 颜色**决定，填错了建索引时会直接报错：

| class | 颜色 | severity |
|---|---|---|
| `fault` | `red` | `stop` |
| `fault` | 其它 | `check_soon` |
| `reminder` | 任意 | `info` |
| `status` | 任意 | `info` |

安全带未系是红色的，但它是 `reminder`，级别是 `info` 而不是 `stop`。这张表存在的理由就是这一条。

### 受控词表：只能用这些词

描述子是给检索用的，不是给人读的。**写词表以外的词会被判越界**。

- **shape**：`person` `lamp` `circle` `triangle` `rectangle` `car_outline` `battery` `engine` `wheel` `thermometer` `droplet` `wrench` `steering_wheel` `letter_only` `other`
- **color**：`red` `amber` `green` `blue` `white` `gray` `black` `unknown`
- **elements**：`diagonal_band` `parentheses` `wavy_lines` `straight_lines` `exclamation` `arrow_left` `arrow_right` `arrow_both` `cross` `check` `plus` `minus` `slash` `circle_ring` `none`

### 描述子来源这一列，决定了你能不能信这张表

- `manual-image`：**对着手册图标逐条核对过**。只有这一档能进生产。
- `standard-symbol`：按 ISO 2575 通用符号起草，还没对图。可以先建索引跑通，但一定要回来对图。
- `deprecated`：**这个符号在你的手册里其实不存在**。保留占位行但不进索引、不参与匹配、不参与合成。

未对图的目录可能包含手册里不存在的符号、画错的描述子与标错的评测真值，**其错误率未经测量，不能视为零**。Tesla 目录的起草稿对图后查出一枚手册中不存在的「前雾灯」、五条画错的描述子与一条标错的评测真值。

### 先对图，再写描述子

顺序反过来会把预想的画法写进表里，错误随之传到合成与匹配。顺序是：裁图 → 把图排开逐个看 → 写描述子 → 再回头核一遍。

## 第 3 步：建图文索引

```bash
set -a; source .env; set +a
corepack pnpm kb:icons data/kb-src/icons/<你的车型目录>-indicators.md --rebuild
```

要求：本机 PostgreSQL 在跑且迁移已落成，`.env` 里有 `DASHSCOPE_API_KEY`。

每条会建一条**文本向量**（描述子拼成的中文串）；「图片」列非空且文件存在的再建一条**图像向量**。`--rebuild` 先删掉该车型的旧行，改过表之后重跑要带上它。

预期输出里会报进了多少条、跳过多少条（`deprecated` 的与没图的会被跳过）。**跳过数不为零而你以为应该是零时，先看图片文件名是不是和表里对不上。**

换了 `CABINHUG_ICON_EMBED_MODEL` 之后必须整表 `--rebuild`，向量维度可能变。

## 第 4 步：验一次

拿几张**真实拍的**照片（不是手册截图）登记进评测集，然后跑匹配。

在 `evals/vision-observe/photos/` 放照片，在 `evals/vision-observe/cases.jsonl` 加一行真值：

```json
{"id":"byd-01","file":"photos/byd-01.jpg","provenance":"team-owned","vehicle":"BYD 汉 EV/DM-i","negative":false,
 "frame":{"cut_off_sides":[],"quality":{"blur":false,"dark":false,"glare":false,"partial":false,"occluded":false}},
 "items":[{"category":"warning_light","bbox":[552,195,594,238],"shape":"lamp","color":"green","state":"lit",
           "text":[],"elements":["straight_lines"],"symbol_id":"low_beam","class":"status"}]}
```

`vehicle` 必须和目录表里 `vehicle:` 行**逐字相同**。`bbox` 是 0 到 1000 的归一化坐标 `[x1,y1,x2,y2]`，原点左上。

```bash
node --import tsx --test evals/vision-observe/cases.test.ts     # 真值结构守卫
set -a; source .env; set +a
corepack pnpm eval:vision-observe -- --match --id byd-01
```

报告里看三个数：

| 指标 | 含义 | 判据 |
|---|---|---|
| `M-H1-both` | 双路召回的 hit@1 | 低于 80% 就回去查描述子 |
| `M-G1-both` | 闸门通过**且正确** | 比 hit@1 低很多，说明两个候选分不开 |
| `M-V1` | 成对核验覆盖 | 分母是 0 说明图片没被读到 |

**`M-G1` 明显低于 `M-H1` 时不要去调阈值**，先看是不是两枚图标的描述子写得一模一样。同形符号（比如近光灯和驻车灯都是「绿色 灯形 直线」）在文本路上天然分不开，靠图像路分。这时候要做的是把图片补齐，不是放松闸门。

# 路 B：训练专用小检测器（可选）

做到这里系统已经能认灯了。下面这半段解决的是另一个问题：**把「图标框在哪」这一步从通用视觉模型换成一个自己的小模型**。

这条路在本仓仍是实验状态，合成集上的 mAP **不能当真实召回**。

> 训练服务 `enterprise/backend/vision-trainer` 是内部工具，不随公开仓提供。第 6 步至第 11 步中调用它的命令需要你自备训练环境；控制台「模型训练」页通过 `VISION_TRAINER_URL` 连接训练服务，未配置时该页显示不可用。开始之前请确认你有 30 张以上真实拍的照片可以用来验收，没有的话训出来的东西无法判断好坏。

## 第 5 步：准备真实屏幕底图

合成的意义在于「图标出现在它真实会出现的地方」。所以底图必须是**真实拍的屏幕/仪表照片**，数量几百张起。

来源可以是行车记录仪抽帧、工程车队的采集素材、或有明确许可的公开数据集。放成这个结构：

```
evals/vision-observe/datasets/<你的底图集>/
  <任意分组>/images/*.jpg
```

**许可要登记。** 用了公开数据集就在 `evals/vision-observe/datasets/README.md` 里写清出处、许可与署名对象。

## 第 6 步：筛负样本

负样本是「一盏灯都没亮」的照片，用来量误报。**判据是像素，不是模型。**

不用观察层粗筛：1920×1080 整帧里一枚图标只有约 30 像素，模型会把亮着灯的帧判成「零警示灯」。实测 15 张候选全被判为零警示灯，其中 7 张亮着两盏绿灯。

现成的筛选脚本在 `enterprise/backend/vision-trainer/vision_trainer/tools/pick_negatives.py`，判据是「图标列里有没有偏离该列背景色的像素」。**它目前把底图目录写死成了 Tesla 那一套**，你需要改 `FRAMES` 常量指向自己的目录，并按第 7 步重新标定 `COLOR_DEVIATION` 与 `COLUMN_MIN_LUMA`。

```bash
cd enterprise/backend/vision-trainer
uv run python -m vision_trainer.tools.pick_negatives --scan 20 --out neg.json --sheet-out neg-columns.jpg
```

**筛完必须人眼逐张过放大的图标列。** 一张其实亮着灯的负样本，等于教模型别去认那盏灯，比没有负样本更糟。

过目通过的复制进 `evals/vision-observe/negatives/`，在 `cases.jsonl` 里写 `"negative": true` 且 `"items": []`，在 `negatives/README.md` 登记来源与许可。

**入库时不要缩放、不要重压缩。** 触发误报的小图标缩小后不再触发，样本因此失去回归基线的作用，且不报错。实测：7 张截图从 1672×941 缩到 1280×720 后，同一模型在同样的图上从 7/7 误报变为 0/7。

## 第 7 步：标定几何常数（必需）

合成器与筛选脚本里的所有几何数字都是**在 Tesla 的横屏中控上量出来的**。你的车如果是竖屏、是传统仪表盘、或者指示灯排在别的位置，照抄这些数字合成出来的图标会落在错误的地方，**且不报错**。

**相对坐标必须在完整屏幕的照片上量。** 用裁掉部分屏幕的特写照片当尺度参照时，「屏幕宽」的分母不同，合成的图标会落在地图面板上。

### 要标定的三组常数

**第一组，屏幕定位**（`vision_trainer/tools/screen.py`）：

| 常数 | Tesla 的值 | 含义 |
|---|---|---|
| 面积占比 | 0.20 – 0.80 | 屏幕占整幅画面的比例 |
| 宽高比 | 1.2 – 2.6 | 横屏中控。**竖屏或方形仪表必须改** |
| 亮度阈值 | 均值 + 18，下限 70 | 屏幕是暗车内背景上的亮矩形 |

验证方法：

```bash
cd enterprise/backend/vision-trainer
uv run python -m vision_trainer.tools.composite --check-screen 20 --sheet screen-boxes.jpg
```

打开 `screen-boxes.jpg`,20 张里应该 20 张都画出了框，且框贴着屏幕边缘。定不出来的帧会被合成时跳过，**跳过比乱贴好**，但成功率低于八成就说明常数不对。

**第二组，图标列的位置与尺度**（`vision_trainer/tools/composite.py`）：

| 常数 | Tesla 的值 | 含义 |
|---|---|---|
| `ICON_W_MIN/MAX` | 0.018 – 0.030 | 图标宽度占**屏幕宽**的比例 |
| `COL_X_MIN/MAX` | 0.014 – 0.042 | 图标列的横向位置，占屏幕宽 |
| `COL_Y_MIN/MAX` | 0.19 – 0.60 | 图标列的纵向范围，占屏幕高 |
| `ROW_GAP_MIN/MAX` | 0.050 – 0.075 | 竖排间距，占屏幕高 |

量法：找一张**屏幕完整入镜、且有两枚以上指示灯亮着**的照片，用任何看图工具读出屏幕四角坐标和每枚图标的框，然后算比值。多量几张取范围。

**第三组，融合强度**（同一文件）：

| 常数 | Tesla 的值 | 含义 |
|---|---|---|
| `CONTRAST_MIN/MAX` | 26 – 105 | 图标笔画比背景暗多少（**贴之前的目标值**） |
| `SAT_MIN/MAX` | 22 – 175 | 笔画饱和度目标值 |

这两组填的是**贴之前的目标**，要比期望的实测值高一档：后续的模糊与 JPEG 压缩会吃掉大约三成。按实测值直接填时，落地后的中位对比度为 16，低于真实照片的 18。

## 第 8 步：合成训练集

```bash
cd enterprise/backend/vision-trainer
uv run python -m vision_trainer.tools.composite \
  --catalog ../../../data/kb-src/icons/<你的车型目录>-indicators.md \
  --frames ../../../evals/vision-observe/datasets/<你的底图集> \
  --name <你的合成集名> --train 400 --val 100 \
  --result-sheet synth-boxes.jpg --compare real-vs-synth.jpg
```

它做四件事：定位屏幕 → 随机挑 1 到 5 枚图标竖排放进图标列 → 四道融合（亮度对齐、模糊、噪点、整图 JPEG）→ 写图与 YOLO 标注。输出的是**屏幕裁剪**而不是整帧，整帧里一枚图标只有 30 像素，缩到 640 的训练尺寸就剩 10 像素，学不到。

类别数等于目录里非 `deprecated` 且有图片的条目数。红色故障类默认加 3 倍权重——那些灯正常行车永远拍不到，只能靠合成补。

**两张图必须打开看**：

- `synth-boxes.jpg`：标注框贴不贴图标、图标在不在该在的位置。
- `real-vs-synth.jpg`：左边真实亮灯、右边合成，并排比边缘锐利度与饱和度。分得出来就说明融合不够，回第 7 步调对比度与饱和度。

**合成图只进训练集，一张都不能进 `cases.jsonl`。** 评测集混入合成图会让评测失去独立性。

## 第 9 步：在控制台训练

起服务：

```bash
corepack pnpm dev:restart vision-trainer
curl -s localhost:8799/health
```

服务只绑 `127.0.0.1:8799`，鉴权在网关。网关侧要在 `.env` 里配 `VISION_TRAINER_URL=http://localhost:8799`，否则控制台页面会显示「未配置」。

打开运营控制台的**「模型训练」**页（`/vision-trainer`），在「数据集」里选你刚合成的那个，填参数：

| 参数 | 建议 | 说明 |
|---|---|---|
| 基座 | `yolo11n.pt` | 最小的一档，够用且快 |
| 轮数 | 30 | 是上限不是目标，早停会提前收 |
| 早停耐心 | 10 | 连续 10 轮不涨就停 |
| 图像尺寸 | 960 | 图标小，640 会糊掉 |
| 批大小 | 8 | 显存不够就调小 |

页面上能看到实时进度、每轮的 mAP50 与 mAP50-95。跑完模型出现在模型列表里。

**mAP50** 是框重合一半就算对的宽松口径，**mAP50-95** 从一半到几乎完全重合取十档平均，是严格口径。合成集上这两个数**都不能当真实召回**：正样本全是贴上去的，模型可能学到了合成痕迹。

## 第 10 步：测试验证与误报对照

页面下方的「测试推理」可以上传照片，或直接从评测集里挑，结果会把预测框（实线绿）与真值框（虚线琥珀）叠在一起画出来。

**真正要看的是误报对照，不是 mAP。** 拿同一批负样本、同一套推理参数，跑新旧两个模型各一次，比「有误报的张数」和「误报框总数」。

本仓的实测对照：

| 模型 | 有误报的负样本 | 误报框 | 真实屏幕帧 | 与车无关的界面截图 |
|---|---|---|---|---|
| 同源合成训出的旧版 | 19/20 | 43 | 12/13 | 7/7 |
| 真实底图训出的新版 | 4/20 | 14 | **0/13** | 4/7 |

同时**必须**拿真实照片试一次。上表的新版在一张真实照片上 4 枚真值全部未命中，合成集指标不反映真实召回。**没有真实照片验证，这一步不算完成。**

## 写死为 Tesla 的四处，接自己的车必须改

下面四处硬编码按 Tesla 的假设工作，**不改时不报错**：

| 位置 | 现状 | 你要做什么 |
|---|---|---|
| `vision_trainer/tools/pick_negatives.py` 的 `FRAMES` | 写死 Tesla 底图目录，没有命令行参数；分层抽样按「文件名第一个下划线之前」当视频号 | 改常量指向自己的目录；文件名不是这个形状时分层会退化成不分层 |
| `vision_trainer/tools/composite.py` 的几何与融合常数 | 在 Tesla 横屏上量的 | 按第 7 步重新标定 |
| `vision_trainer/tools/screen.py` 的面积与宽高比门 | 按横屏中控设的 | 竖屏或仪表盘必须改 |
| `evals/vision-observe/run.ts` 的 `iconsDir` | 写死 `data/kb-src/icons/tesla-model3` | 改成自己的目录，否则 `--match` 的核验用的是别人的图 |

另有一条行为约束：图标索引里**只有一款车**时，生产链路能自动认出该用哪份图标目录；有两款及以上且车辆档案里没登记具体车型时，系统**不做成对核验**（返回「疑似」而不是「是」）。拿别的车的图核验，模型会答「不一样」，表现为有图却总对不上，比不核验更难排查。接第二款车之前，先确认车辆档案里的车型串能传到观察层。

## 常见错误与现象

| 现象 | 多半是什么 | 去哪儿看 |
|---|---|---|
| `kb:icons` 报 `缺 vehicle: 行` | 目录 md 头部没写 `vehicle:` | 第 2 步 |
| `kb:icons` 报 `severity 与 类别×颜色 表不符` | severity 是算出来的不是填的 | 第 2 步的二维表 |
| 建索引时图像向量数远少于条目数 | 图片文件名和表里对不上，或文件不在 `<目录名>/` 下 | 第 1 步的命名要求 |
| 匹配结果永远是「疑似」，不说「是」 | 成对核验没跑：图片读不到，或索引里有多款车而档案没说是哪款 | 上一节最后一条 |
| `M-G1` 远低于 `M-H1` | 两枚图标的描述子写得一样，文本路分不开 | 第 4 步的说明 |
| 合成出来图标落在地图面板上 | 相对坐标是在裁过的特写照片上量的，分母错了 | 第 7 步 |
| 合成图并排一眼看得出是贴的 | 对比度或饱和度目标值偏高，或色度放大过头 | 第 7 步第三组常数 |
| 控制台「模型训练」页显示未配置 | `.env` 缺 `VISION_TRAINER_URL` | 第 9 步 |
| 训练页有数据集但训不动 | 服务没起，或这台机器没有可用的 GPU/MPS | `curl localhost:8799/health` |
| 模型 mAP 很高但真实照片认不出 | 学到的是合成痕迹 | 第 10 步，这是预期内的 |
